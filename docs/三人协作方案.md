# 三人协作方案

## 1. 记录原则

采用 A 数据库、B 后端、C 前端三个角色模拟协作组织。角色代表任务责任，不等于有三位真实同学参与。本轮实际执行者为 Codex，用户提供方向与范围；未产生真实成员之间的复核记录。

后续有真实组员时再登记姓名、认领任务并由实际参与者完成总结。Git 使用实际操作者身份，不切换虚构作者来制造贡献历史，不补造讨论、工时、签名或评审意见。

## 2. 职责与交付物

| 角色 | 主责 | 主要交付 | 协作边界 |
| --- | --- | --- | --- |
| A 数据库与 SQL | 数据字典、E-R、关系模式、3NF、约束、索引、SQL、触发器、过程 | 设计文档、数据库脚本、查询示例、验证记录、报告数据库章节 | 定义 SQL 和一致性规则；与 B 确认事务执行方式 |
| B 后端与架构 | 架构、原生 SQL 数据访问、接口、事务调用、模拟时间 | 架构图、接口约定、后端代码、运行说明、接口验证、报告后端章节 | 负责开始/提交/回滚事务及连接生命周期；不得重复执行触发器已经承担的记账 |
| C 前端与展示 | 页面流程、四类可视化、接口消费、联调和演示 | 原型、前端代码、页面证据、演示流程、报告前端章节 | 与 B 先对齐字段、日期、金额和错误响应；与 A 对齐统计口径 |

A 主责数据库定义与公共 SQL 脚本；B 编写接口中使用的原生 SQL，并与 A 校对。不能将原文“成员 A 编写 100% SQL”理解为 B 无需理解或维护自身接口查询。

## 3. 任务认领与验收

任务编号按角色和类别命名，例如 `A-DB-01`、`B-API-01`、`C-UI-01`。跨角色任务仍指定一个主责角色，另列协作角色。

每项任务记录以下信息：

```text
任务编号/名称：
关联要求：R-xx
主责角色：
实际执行者：
协作角色/实际复核者：
前置任务：
交付文件：
验收条件：
实际验证方式与结果：
关联 Git 提交：
状态：待开始 / 进行中 / 待验证 / 已完成 / 受阻
遗留问题：
```

“已完成”必须有文件和适当验证；计划分配给 B 的任务不能直接算作 B 已完成。无实际复核时写“未复核”；由同一 agent 自检时写“自检”，不冒充另一位成员复核。

所有记录集中在《协作记录.md》，交接只保留摘要，避免重复维护多份状态。

## 4. 三人如何衔接

1. 三角色先对齐业务规则、数据字典和统计口径，A 汇总数据库版本。
2. B 根据数据模型与 C 的页面需求维护接口约定，说明字段、类型、分页、错误、日期及金额格式。
3. A 交付可重建数据库和虚构测试数据，B 跑通基础接口；C 可先用明确标注的模拟数据搭页面。
4. C 切换到实际接口后，与 B 逐项验证；A 协助检查结果与数据库是否一致。
5. 每个阶段将验证证据归档，再更新任务状态、交接与 Git 节点。

字段、表结构、统计口径或接口变化时，由主责角色提出并同步影响文档和调用方。没有真实组员时，同一执行者可以依次切换角色完成任务，记录实际执行情况即可。

## 5. Git 与贡献说明

本地一个仓库即可满足当前进度留痕；不为模拟协作额外创建三个虚构账户。当前阶段在现有 `master` 分支保存阶段节点，真实多人开发时再按需要使用独立分支或 worktree。

提交示例（仅说明格式，非完成记录）：

```text
docs(A-DB-01): 完成需求分析与数据字典
feat(A-DB-03): 完成建表约束和初始化数据
feat(B-API-02): 跑通订阅基础接口
feat(C-UI-02): 完成订阅管理页面
```

多人共用机器时采用真实参与者身份或在说明中记录真实贡献，不伪造 `--author`。无需按照提交次数或代码行数平分工作；成果、复杂度、验证和解释能力共同说明贡献。
