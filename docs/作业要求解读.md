## 2. 题目与业务边界

题目：**基于原生 SQL 的个人数字资产与订阅服务管理系统**。

面向个人使用，解决自动续费遗忘、多个支付渠道扣款难以汇总、数字资产长期闲置等问题。保留用户实体用于数据归属；原文不要求多租户、复杂权限、真实支付接入或真实账号托管，当前均不纳入默认范围。

原文列出 8 个核心实体；原文括号中提及“6—8 个要求”，其教师来源仍待核对。以这 8 个实体为设计基线，避免无说明增减。

| 实体 | 业务职责 | 设计时需要明确 |
| --- | --- | --- |
| 用户 User | 标识个人及数据归属 | 演示用户及归属一致性 |
| 支付方式 Payment | 管理支付渠道 | 订阅默认支付渠道与历史实际支付渠道的区别 |
| 订阅服务 Subscription | 价格、周期、状态、续费管理 | 状态变化、续费成功条件、日期计算 |
| 扣费记录 BillingHistory | 保存财务历史 | 历史金额保留、取消事件与支出的区别 |
| 数字资产 DigitalAsset | 管理持有资产和使用情况 | 资产与订阅的基数、未使用的处理 |
| 账号密码库 Vault | 关联账号凭据信息 | 仅使用虚构演示信息；凭据处理方案单独设计 |
| 待办与提醒 Reminder | 续费、超支等提醒 | 类型、来源、状态及撤销范围 |
| 预算与控制 BudgetControl | 设置预算并提供控制依据 | 预算周期、适用范围、重复提醒规则 |

上表是职责说明，尚不是最终字段、关系模式或 E-R 图。

## 4. 报告目录及准备方式

系统设计报告：

1. 需求分析：背景与目标、功能模块图、顶层及 0 层数据流图、数据字典。
2. 概念结构：局部 E-R 图及全局 E-R 图。
3. 逻辑结构：各表关系模式、候选键与函数依赖、3NF 分析和必要优化。
4. 物理结构：索引名称/表/字段/类型/依据、存储引擎选择。

系统实现报告：

1. 系统总体架构图与技术栈说明。
2. 基本表的原生 SQL 定义。
3. 触发器与存储过程的 SQL、业务逻辑和验证结果。
4. 功能 SQL 及运行结果，重点包括复杂查询和事务。
5. 前端技术、页面截图与可视化说明。
6. 每位实际成员的个人总结，说明真实工作与理解。

开发过程中先维护可追踪的 Markdown、SQL、图片等材料，最后整理为 Word。不能用 Markdown 文档代替原文最终要求的 Word 报告，也不能在功能尚未运行时填入虚构截图或结论。
