# 高级数据库功能方案（已设计，尚未实现）

第 8 周只交付本方案和支持未来实现的基础字段。**数据库目前没有触发器、存储过程，也没有取消或续费执行接口。**本文件中的步骤是后续实施约定，不是已运行的 SQL 或测试结果。

## 一、取消订阅事务

职责：A 定义 SQL、约束和业务不变量，B 在同一连接显式 begin/commit/rollback，C 展示确认和结果。不是三个角色各维护一套取消代码。

目标执行步骤：

1. 校验 subscription_id 和业务日期；开始事务。
2. 通过支付方式关联检查用户归属，`SELECT ... FOR UPDATE` 锁住订阅。
3. 如果已取消，返回既有取消结果，不追加事件；若无 CANCEL 说明历史数据不完整，返回一致性错误并人工检查。
4. 将订阅 status 更新为 cancelled，auto_renew 设为 false。
5. 向 billing_history 插入 `CANCEL, amount=0, payment_id=NULL`；event_key 为 `cancel:<subscription_id>`。取消操作由事务写入，续费触发器不得在 status 变化时误写 CHARGE。
6. 将该订阅 `kind='renewal' AND status='pending'` 提醒改为 revoked；不撤销 done 或预算提醒，不碰其他订阅。
7. 所有步骤成功后提交，任何失败回滚；锁冲突按可识别错误返回，后续可有限重试整个事务。

取消不是 DELETE。已存在流水/资产/提醒的订阅当前删除会被 RESTRICT 阻止。后续不得为方便界面而放宽约束。

验证计划：正常取消、已取消重试、其他用户/不存在记录、中间步骤故障注入、提醒过滤、并发续费与取消。故障注入必须发生于测试环境；验证表中状态、历史和提醒均保持取消前值。第 8 周基础 CRUD 的事务包装不等于已经完成本取消事务。

## 二、续费记账触发器

不要用“next_billing_date 变了”作为成功续费信号，因为基础接口允许修正预计日期。后续迁移将为 subscription 增加 `renewal_seq`、`last_renewed_on` 两个状态字段：

- renewal_seq 初始 0，只由专用续费命令递增 1；值代表已确认成功续费次数，是业务状态而非流水 COUNT 缓存。
- 续费执行前锁 subscription、确认 active/auto_renew、校验应到期日、锁对应月预算；调用方提供幂等请求键或 expected_seq 防重复。
- 在同一 UPDATE 中设置实际业务续费日期、下次预计日期并增加序号；按原锚定日计算月份末日，明确 1 月 31 日等边界规则。
- AFTER UPDATE 触发器仅当 `NEW.renewal_seq = OLD.renewal_seq + 1` 且状态允许时插 CHARGE，金额取本次确认价格，payment_id 取当时支付方式，event_key 为 `renew:<id>:<seq>`。
- 普通 PATCH 不得修改这两个字段；后端不再插相同流水。event_key 唯一约束是最后一道重复保护，重复应使整个续费事务回滚。

迁移前先检查既有事件，不从当前样例次数猜测真实续费序号。若需要未来多用户按历史渠道统计，续费入口还应验证支付方式所有权不可跨用户混用。

验证计划：正常续费一次一条、普通编辑零条、相同请求重试不再增加、取消后不可续费、非法序号跳跃、触发器插入失败导致原 UPDATE 回滚、月末/闰年/并发请求。

## 三、扣费预算预警触发器

AFTER INSERT ON billing_history，只处理 CHARGE。由订阅归属用户和 occurred_on 计算 month_start，按自然月汇总所有 CHARGE，CANCEL 不参与。预算不存在时不自动创建预算、不生成“零预算”超支警告。

超支条件为月累计 > 预算；等于预算不超支。提醒与触发超支的订阅关联，但去重键按 `budget:<user_id>:<YYYY-MM>` 生成，因此同用户同月最多一条预算预警。提醒正文是生成时快照，保留历史意义；后续界面可另查实时预算值。

一致性约定：所有扣费入口先锁同一月 budget_control 行，再更新订阅触发记账；汇总使用能看到此前已提交扣款的读取语义。专用写入连接拟采用 READ COMMITTED，并统一锁顺序，避免不同订阅并发扣款各自只看到局部结果。直接绕过入口的并发手工 INSERT 不在该保证内，应限制数据库写权限或提供受控过程。不能仅靠“有触发器”就宣称所有并发预算都正确。

触发器内再次定位/锁定预算，并以唯一 dedup_key 防重复。发生异常不得吞掉并提交半条业务。后续应基于 MySQL 具体锁行为做双连接并发验证，再确认实现。

验证计划：未超支、恰好预算、第一次超支、继续扣款不重复、CANCEL 不触发、无预算、跨月、相同用户两订阅同时跨过阈值、故障回滚。

## 四、月度汇总存储过程

建议名称 `sp_monthly_summary(IN p_user_id BIGINT, IN p_year INT, IN p_month INT, IN p_as_of DATE)`。包含原文要求的年/月参数，增加用户和基准日使归属和闲置判断可复现。非法年月用 SIGNAL 明确报错。

返回三个结果集：

1. 支付方式：按 billing_history.payment_id 关联渠道，汇总该自然月 CHARGE，保留历史实际渠道。
2. 服务类型：按订阅类别分组，同月同事件过滤；本轮类别不允许接口修改，暂按当前类别。
3. 闲置资产：严格早于 `DATE_SUB(p_as_of,INTERVAL 3 MONTH)`；从未使用则取 acquired_on；只返回 active 且 auto_renew 的所属用户资产，包含订阅名和有效最后使用日。

B 通过原生游标 `CALL`，依次读取全部结果集；不只读取第一个结果集。若报表需要同一时点快照，显式只读事务中调用。未来是否同时统计零支出渠道应在接口契约固定：拟返回用户所有渠道，金额无记录时补零。

验证计划：种子年月、无流水月份、取消事件排除、同名类别、没有使用日期、恰好三个月、非自动续费资产、多结果集读取、非法年月。
