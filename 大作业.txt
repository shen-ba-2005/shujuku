# 《个人数字资产与订阅服务管理系统》大作业实施指南

## 一、 项目基本信息
*   **题目名称**：基于原生SQL的个人数字资产与订阅服务管理系统
*   **团队人数**：3人
*   **开发环境**：MySQL（推荐）或 PostgreSQL / SQL Server
*   **技术约束**：允许使用 Web 高级框架（如 Django, Spring Boot 等）辅助实现前后端功能及数据库连接，**但所有涉及数据库的数据定义和操作均必须使用原生 SQL 语句实现（绝对禁用 ORM）**。

## 二、 项目核心业务说明
本系统面向单用户（个人），旨在解决现代人“自动续费易忘取消、多平台扣费混乱、虚拟资产吃灰”的痛点。
**系统包含8个核心实体（完美符合6-8个要求）**：
1. 用户表（User）
2. 支付方式表（Payment）
3. 订阅服务表（Subscription）
4. 扣费记录表（BillingHistory）
5. 数字资产表（DigitalAsset）
6. 账号密码库表（Vault）
7. 待办与提醒表（Reminder）
8. 预算与控制表（BudgetControl）

## 三、 硬性开发要求（严格对照大作业评分点）

### 1. 数据库设计与实现（DDL）
*   **禁止ORM建表**：必须手写 `CREATE TABLE` 语句建表，手写约束（主键、外键、唯一性、非空）、手写索引。
*   **范式要求**：所有关系模式必须达到 **3NF**。例如：订阅表和扣费记录表必须分离；扣费记录表不应包含订阅服务的名称，仅通过外键关联。
*   **物理设计**：在经常查询的字段（如：下次扣费日、状态、外键）上建立合理的索引，并在报告中说明建立依据。

### 2. 数据库操作与逻辑（DML & PL/SQL）
*   **禁止ORM查询**：后端代码中不允许出现 `Model.objects.filter()` 或 `Repository.findBy...` 等框架封装方法。必须手写 `SELECT`, `INSERT`, `UPDATE`, `DELETE` 原生SQL语句，通过 JDBC/数据库游标执行。
*   **复杂查询**：必须使用原生 SQL 的多表联查（`JOIN`）、分组聚合（`GROUP BY`）、子查询来实现前端的统计报表。
*   **事务（Transaction）**：必须实现“取消订阅”功能。手动开启事务，依次执行：更新订阅状态 -> 写入扣费终止记录 -> 撤销相关未完成提醒。任何一步失败必须 `ROLLBACK`。
*   **触发器（Trigger）**：必须手写至少 2 个触发器。
    *   *触发场景1*：当“扣费记录表”插入新数据时，自动对比“预算与控制表”，若超支，自动向“待办提醒表”插入一条警告。
    *   *触发场景2*：当订阅服务发生续费更新时，自动向扣费历史表写入流水。
*   **存储过程（Stored Procedure）**：必须手写至少 1 个存储过程。传入年份和月份，自动汇总各支付方式、各服务类型的支出总额，并扫描输出“超过3个月未使用且仍在自动续费”的闲置资产。

### 3. 系统架构与前端
*   **架构设计**：采用前后端分离架构。画出系统总体架构图。
*   **前端开发**：界面友好，必须包含：仪表盘看板、扣费日历、资产闲置饼图、预算进度条（可用 ECharts 等库辅助展示）。允许借助 AI 生成前端 UI 代码，但必须理解其逻辑。

## ⚠️ 答辩保命指南（注2要求）
1.  **绝对不许用 ORM**：如果后端代码中出现 `save()` 或 `filter()` 等对象映射方法，直接扣分。必须用类似 `cursor.execute("SELECT * FROM ...")` 的方式。
2.  **必须能解释原理**：老师会问“你为什么在这里用触发器而不是在后端代码里写？”你要回答：“为了保证数据一致性和实时性，因为扣费记录一旦产生就必须立刻校验预算，放在数据库层执行效率最高且解耦了应用层逻辑。”
3.  **不要盲目依赖 AI**：AI 可以帮你写前端页面，帮你查语法错误，但**数据库的 E-R 图、3NF 逻辑、触发器的具体 SQL 逻辑**，你必须自己懂，答辩时说不清楚会降级。
